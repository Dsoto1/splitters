# Tile Trigger: notes for Claude sessions

Start with `docs/QUEUE.md` (the short list: in flight, bugs, easy wins, features, waiting on the owner; keep it current in the commit that lands an item), then `HANDOFF.md` (current state, claims, history) and keep it current when you finish work.

Session memory: at the end of a session, write `.control-center/session-summary.json` (title, summary, decisions, tasks; no secrets); the session hook sends it to the Project Control Center.

## Git workflow
- Work on the session branch; no pull requests unless asked.
- Before pushing a merge candidate: merge `origin/main` first, then `pnpm prepush` on that commit (it refuses until main is merged in and the tree is clean, then runs the typecheck, the content check and `pnpm test:changed`, and prints the flows CI will run; `--e2e` runs them). Checks that passed before the merge don't count: main may have gained a check your change breaks.
- The checks it runs, for a branch still in work: `pnpm typecheck`, `pnpm test:changed` (vitest on what changed vs origin/main) and `pnpm e2e:changed` (after `pnpm build`: the e2e flows `e2e/flowMap.mjs` maps your changed files to; one flow by hand: `E2E_ONLY=<flow> node e2e/run.mjs`). Agents use these two rather than picking tests by hand.
- CI on a check branch runs only what the change needs since origin/main, or since the nearest ancestor already green on a check branch (`pnpm ci:plan` shows it; unmapped paths run everything, docs nothing) and a push to `main` already green on a check branch isn't re-run; nightly, `v*` tags and Run workflow run everything, and only they take the browser map tour (every map, 14 parts); elsewhere the headless all-maps unit test (`packages/shared/test/allMaps*`) and the coverage map's flow (`maps/test_coverage.json`, one of everything; its unit test fails when new content is missing from it) stand in, and a change to a few maps tours just those. E2E runs on up to 16 shards packed by measured flow time (`e2e/timings.json`, refreshed by CI's timings job). A new push to a check branch cancels its older run, and a check branch's unit and e2e shards all run to the end, so one push shows every failure (the run reads failure); elsewhere (main, nightly, tags), and for the perf and bots steps everywhere, the steps stop once any job fails (`tools/ci/stop-on-failure.sh`; the run reads failure). E2E: `?test=1` for determinism, wait on conditions (no new `waitForTimeout`), screenshot baselines via `pnpm e2e:baselines`.
- The full suite runs on GitHub, not locally: push a merge candidate to a `check/<name>` branch (`git push origin HEAD:check/<name>`); CI (unit tests, build, the e2e shards the change needs) runs there. Fast-forward `main` only to a commit that went green on a check branch.
- Landed branches go by themselves: after each push to `main`, the Prune branches workflow (`.github/workflows/prune-branches.yml`) deletes every `wip/` and `check/` branch whose commits are all in main. Agents can't delete branches (their GitHub access only creates and moves them), so leave them.
- Several green branches at once: `node tools/ci/train.mjs wip/a wip/b …` merges them in order onto origin/main (stops on a conflict, naming the branch and files) and pushes `check/train-<timestamp>`; once its run is green, `node tools/ci/train.mjs --land <sha>` fast-forwards `main` (only if that branch's latest run is for `<sha>`, completed and successful, and main hasn't moved). It never force-pushes. A commit whose code equals a green check commit (only docs differ) isn't re-run either.
- Process tools (owner, 2026-11-18; docs/PROCESS.md):
  - `node tools/ci/train.mjs --ready` confirms QUEUE's "Ready to land" entries from GitHub (latest run on the check branch completed+success for that sha, branch unchanged but for docs, not on main) and prints the landable ones; `--ready --run --holder X` runs the train on them.
  - A train resolves conflicts that are only in HANDOFF.md and docs/QUEUE.md by itself (the candidate's side plus the branch's added lines); anything else still stops it, naming the branch and files.
  - `e2e/run.mjs` serves on 127.0.0.1 and, off CI, picks free ports unless `E2E_CLIENT_PORT`/`E2E_SERVER_PORT` (and the flows' hub/control port variables) are set, so parallel worktrees don't collide; `CHROMIUM=<path>` launches that browser binary.
  - `node tools/dev/cleanup.mjs` lists finished worktrees (clean, merged or pushed, idle 2 h), idle build output and /tmp compile caches; `--yes` removes them and prints the space freed. It never touches uncommitted work.
  - `node tools/ci/flakes.mjs` writes `docs/FLAKES.md`: checks that failed then passed on the same code in the last 7 days of CI runs, with counts; lane A works it in the daily fix batch.
- **Landing (owner, 2026-11-16): check in parallel, land in trains.**
  1. **Check without waiting.** When a branch is finished, merge `origin/main` once, run `pnpm prepush`, and push it to its own `check/<name>`. Do this right away, with no turn or lock, alongside other branches. At most 4 check runs in flight across both lanes; count them in HANDOFF's "Checking" lines.
  2. **Ready to land.** Once its run is green, the branch goes on QUEUE's "Ready to land" list as `branch · green sha · run`, and leaves "Checking". A red run is its owner's to root-cause and fix. Re-run a known flake at most once.
  3. **Trains.** One landing at a time, held by **the landing lock: the branch `landing-lock`** (owner, 2026-11-17; `tools/ci/landingLock.mjs`). Its tip commit says "held by <session>, train <branch>, <UTC time>" or "free"; it never merges anywhere and only grows (never force-pushed or deleted). `node tools/ci/train.mjs --holder "<session>" wip/a wip/b …` takes it as the train starts (it refuses, naming the holder and the lock's age, if someone else has it), keeps it while the check runs, and gives it back if it stops before pushing; `--land <sha> --holder "<session>"` frees it right after the fast-forward. Landing by hand (merging and pushing `main` yourself): `--lock --holder X` first, `--unlock --holder X` after. `--lock-status` shows who holds it and for how long; `--force-unlock --holder X` frees a lock held 3 h or more (a dead session's), with a warning. The holder may also come from `LANDING_LOCK_HOLDER`. The landing turn (either lane's lead) runs the train on every "Ready to land" branch in list order. That makes one combined check run. If it's green, `--land <sha>` lands it. If only docs reached main meanwhile, `--land` refuses: run the train again; its code equals the green commit, so CI skips it. Run a train when 2 or more branches are ready, or when one has waited 2 hours. A single ready branch whose green commit still sits on main (only docs added since) may land alone: merge origin/main and push to `main`. A bug breaking `main` may land alone ahead of the list.
  4. **A red train.** A known flake gets one re-run. If a failure is in one branch's files, drop that branch from the train and run again without it; the branch goes back to its owner. A conflict stops the train, naming the branch; that branch's owner merges and re-checks (conflicts only in HANDOFF.md and docs/QUEUE.md the train resolves itself when they're a simple union of added lines).
  5. Claims (files, map format numbers) still go in HANDOFF before work starts. Two branches touching the same map or generated tables say so in their claims, and land in separate trains if they conflict.
- Push the session branch, then fast-forward `main` to it: `git push origin HEAD:main`. CI runs on every push to `main`; if it goes red, fix forward on `main` the same way.
- Agents: run at most 2–3 at a time; commit at every milestone (a restart loses uncommitted work); run only the tests and e2e flows your change touches.
- Fix batches (owner, 2026-11-17): fixes go to lane A and land once a day as one batch: a branch `wip/fixes-<YYYYMMDD>`, one commit per fix (each with its own local tests), one `check/` run, one landing, one HANDOFF note listing every fix. If the batch's check fails, split it to find the fix. Urgent fixes (a crash, a game that can't be played, a broken menu or host) land alone at once. Features keep their own check and land in trains.
- Weekly versions (owner, 2026-11-17): the lead cuts a version once a week (minor while pre-1.0), as below, from a green main: CHANGELOG's Unreleased becomes the version, the menu version is bumped. A release between weeks only for an urgent fix (a patch).
- Changelog lines (owner, 2026-11-18): one line per change in CHANGELOG's Unreleased (what a player or map maker notices), the detail in docs; release notes must stay readable and under GitHub's size limit.
- Pictures (owner, 2026-11-18): whoever reports a visual fix or feature looks at its pictures before calling it done (top-down, from inside, every level of detail where it applies), and the lead looks again before sending them to the owner.
- Releases: semantic versions (see CHANGELOG.md). For a release, bump `packages/client/package.json` (shown on the menu; regenerate the menu baseline) and turn CHANGELOG's Unreleased into the version's section; when `main` is fast-forwarded to that green commit, CI releases it: `vX.Y.Z` and its tag, from that build (tools/ci/client-release.sh). Nobody tags by hand. Minor for features, patch for fixes; 1.0.0 is the public launch.
- If `main` has moved, rebase the session branch onto `origin/main` first.

## Gunplay
- Before changing weapons, recoil, ballistics, damage, TTK or weapon animation, read `docs/GUNPLAY_SPEC.md` (technical design) and `docs/GUNPLAY_DIRECTION.md` (the feel it's tuned for: arcade responsiveness + ballistic depth + modern polish; responsiveness > realism, fun > simulation).

## Multiplayer and hosting
- Before changing networking, the hub, hosting, TURN, AWS infrastructure or map publishing, read `docs/MULTIPLAYER_DIRECTION.md` (the owner's direction: AWS coordinates, player machines compute; no player uploads (only the owner publishes maps, from MapMaker: docs/HOSTING.md, "Publishing maps"); maps are declarative data; small recurring cost).
- Identity: the owner's shared ToshiroPlay Cognito user pool (also used by their Flavius game) with Google sign-in, through a separate "trigger" app client; the hub verifies Cognito tokens against the pool's public keys (no client secret in the site).

## Maps
- Every map, official ones included, is its file in `maps/<id>.json`, made and edited with MapMaker's own tools. No map build scripts and no one-off code for a single map: a piece a map needs goes into MapMaker (palette, inspector, logic) so the owner and players can edit it.

## Accessibility
- Reduce flashing (Options → Accessibility and the pause menu, on by default; docs/LOOK.md, "Reduce flashing") is a seizure-safety setting. No new effect may add a full-screen flash, a white-out or rapid flicker; effects read `reduceFlashing()` and calm themselves with it on (a steady glow instead of crackle, brightness capped and eased in, blinking at most once a second at low contrast, no large saturated-red flash). New effects must pass the flicker check: the e2e flow `flashing` (`E2E_ONLY=flashing node e2e/run.mjs`; WCAG 2.3.1), and a new kind of bright moment gets a moment in it.

## Content rules
- After a merge or a new prop pack, run `pnpm content:rebuild` (props are one file per pack, `content/props/<pack>.json`; it rewrites the generated tables, locks, palette atlases and provenance; docs/CONTENT_PIPELINE.md, "Adding a prop pack").
- No in-game AI generation: players can't make content through an AI service or connector, and can't upload assets.
- Models we generate ourselves on the owner's Meshy subscription are fine to ship (record them in content provenance as Meshy, owned).
- Meshy models the owner shares (their Drive) are **Meshy Community CC0** unless the owner says they created them (owner, 2026-11-06): record them as community CC0. CC0 needs no credit, so the author is optional; the post URL is kept where the owner has it, as proof of the licence. A model whose post says CC BY 4.0 (Meshy's free-plan default) must be credited. Only models the owner says they made, or that we generate through the Meshy API with their approval, are "Meshy, owned".
- Assets the owner buys a full licence for are always allowed (owner, 2026-11-01): record each in content provenance (licence name, "purchased by the owner"), ship only processed output.
- Otherwise only CC0, credit-only human-made, or approved Quaternius packs; never commit raw pack files.
- Sound (owner, 2026-11-06): the **Sonniss GDC Game Audio Bundles** are approved: royalty-free, no credit needed, their own licence (keep its text with the provenance). Ship processed files only, never the raw bundle files. **Freesound**: CC0, or CC BY with credit; never CC BY-NC. Record every sound in content provenance.
- Official and featured servers carry only our own maps: the suite in maps/ and what the owner publishes from MapMaker. Community-hosted servers may run community maps (declarative data, in-house assets only), shown with a clear "Community map" label.
