- **perf budget "starting explosion" over 40 ms** (frost_basin; 41.6 ms Medium on train run 46102299426, 49.3 ms Low on train run 46141903583, attempt 1 each; 2026-11-28, `wip/ci-recurring-1128`). **Cause: the product.** A blast past the one-shot effects' cap (GodotVfx.play returns false: 6 playing on Low, 12 on Medium, which a crowd's fight reaches) falls back to the plain fireball (GameView.explosion), and that built a new 12-segment sphere and a new StandardMaterial for every blast; setting up a material marks every mesh in the scene for a check (`_markAllSubMeshesAsDirty`) and the pieces fed a garbage collection. Measured on CI with a diagnostic perf run (`check/ci-recurring-diag`, run 46154428614: the explosion started 30 more times beside a pure-JS control loop, with a sampling profile): three starts in a row at 58.7, 53 and 34.6 ms while the control loop stayed at its usual 0.8 ms (so not a lost time slice), the profile 226 ms of garbage collection, `_markAllSubMeshesAsDirty` 29 ms and the sphere builder; the slow rounds were the ones with the cap full. The suspect from fix batch 27c (`ShaderPort.near`'s variants missing from the warm-up) is not it: the `gv_explosion_*` programs in the "built after the loading gate" list are the loading gate's own warm-up finishing in the background on a slow page (`prewarmed` still null when the match started), built long before the probe. **Fix:** the plain fireball is a copy of one sphere in one shared material, faded by its visibility (`plainBlast`). Before/after: the diagnostic run with the cap filled first (`check/ci-recurring-diag`, rounds 5-9) and the same with the fix (`check/ci-recurring-diag-fix`): see HANDOFF.

- **e2e characters3** "the Laser Rifle carries a red dot…" held `core.rifle` (train run 46141903583, attempt 2; the scope check's marksman the same way on run 42679874806, 2026-11-09; 2026-11-28, `wip/ci-recurring-1128`). **Cause: the test.** gripsInPlay plays a Deathmatch with a dozen bots and let the round end: a round reaches its score limit in about two minutes, and the next round spawns everyone afresh with the spawn loadout, the rifle in hand (Military set), alive throughout (no "dead" in the old trace, `held#3` with no key pressed). - **e2e editor** (also editorux, editortools; 2026-11-28, `wip/editor-flow-1128`): `page.waitForFunction: Timeout 45000ms` after "a random pickup holds a weapon of its category in TEST" or "Test stops the navigation check still running" (check/armory run 46094473575, train run 46109099910). **Cause: the test, not MapMaker.** Leaving Test, the flows pressed Esc and, if MapMaker wasn't back within `T(3000)`, pressed F5, taking that for "Esc only opened the pause menu". `keyboard.press` returns before the page has handled the key; on a busy page (software rendering, a Test still building) the Esc waited in the page's queue past the 3 s, so F5 was sent too. The Esc then went back to MapMaker (the Test was still loading or counting down), and the F5 landed in MapMaker, where it starts a new Test: MapMaker stayed hidden and the wait for it timed out. Reproduced every time by holding the page's main thread for 6 s just after the Esc. **Fix:** `escapeTest` in `e2e/run.mjs` (all four places that leave a Test this way) waits until the page has handled the Esc (a listener after the match's own) and presses F5 only if MapMaker is still hidden then (leaving a Test shows MapMaker in the same task, so hidden means the Test is still on). The product's Esc / F5 handling was right.
